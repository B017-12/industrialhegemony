# Labeling And Mapping Policy

The scene starts as an unlabelled Gaussian splat. Labels are therefore evidence grades, not ground truth.

## Sources

- `structure`: floor, ceiling, and wall planes from RANSAC.
- `heuristic`: pipeline labels (pipe cylinder fits and HDBSCAN clusters) from size in metres, shape features, height above floor and Lab colour. Confidence is 0.2-0.6 on purpose. See `pipeline/classify.py`.
- `vlm`: optional vision-language suggestion from rendered cluster crops.
- `human`: reviewed override in `data/derived/labels_override.json`.

Human overrides always win over generated labels. Generated files may be recreated by the pipeline, so manual review must not be written directly into `scene_objects.json`.

## How a label becomes `human`

Only the review mode in the viewer writes `label_source: human`, and only when a named reviewer presses a key on that object (Tab 8). Every entry records `reviewer`, `reviewed_at` and `review_status`:

- `confirmed`: the reviewer looked at the crop or the live view and agrees with the class;
- `relabelled`: the reviewer changed the class or the display label;
- `rejected`: noise, a fragment of a wall, or not an object; it is hidden everywhere;
- `merged`: a fragment folded into a neighbour (`merged_into`); the parent gets the union box.

A script, an agent or a VLM must never write `human`. VLM output goes to `vlm_labels.json` and is only shown as a suggestion.

Binding an Excel asset in the review mode writes `mapping_method: human_assigned` (confidence 0.45, capped at 0.5). It is still a guess about identity, because the workbook's coordinates are placeholders; the UI keeps it marked as unverified.

## Review workflow

1. Start the backend and the viewer, then open **Review labels** (top bar or Cmd+K).
2. Enter your name once; it is stored in the browser and written into every entry.
3. Optionally run the crop tour, which flies to each object and stores a crop in `data/derived/crops/`.
4. Work through the queue: the P-002 target first, then the other bound objects, then objects along the robot route, then the rest.
5. If a binding moved, rerun `python3 -m pipeline.run` so the missions follow the new object. Then run `node web/scripts/sync-public.mjs`, `npm run snapshot` and `python3 -m app.cache --warm ASSET-014` (from `backend/`) so the offline data matches.

## Procedural Mapping

The workbook's `Scene_Anchors` coordinates are placeholders. Asset-to-object bindings are procedural and must be displayed honestly:

- `procedural_demo_target`: used for `ASSET-014`, capped at confidence `0.5`.
- `procedural_class_match`: used when a visual class is compatible with an Excel asset class, capped below `0.5`.
- `procedural_fallback`: used when no compatible class is left and the asset is bound to a reachable `other` object, capped at `0.25`.
- `human_assigned`: a reviewer bound the asset to this object in the review mode, `0.45` (capped at `0.5`). The pipeline pins it on rerun.
- `video_evidence`: the object's box was projected into the COLMAP-posed video frames and matched to the equipment there (`_analysis/project_objects.py`). Written to `labels_override.json` with the evidence frames in `notes`, `0.45` (capped at `0.5`), and pinned on rerun. The identity is still unverified. Used for P-002, M-004 and VS-002 (`docs/kt/10-equipment-room-ply.md`).

Objects without a record remain scene objects with no telemetry record.

## Review Guidance

Prioritize route-visible and diagnosis-relevant objects:

- pump
- motor
- control valve
- pressure transmitter
- vibration sensor
- tank or cabinet
- pipe segment
- trolley or cage
- sign
- door or wall fixture

When uncertain, keep the label coarse and lower confidence rather than inventing an exact equipment identity.
